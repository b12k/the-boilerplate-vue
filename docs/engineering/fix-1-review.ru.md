# Пункт 1: render pending и бюджеты в миллисекундах

Базовый коммит: 48c9130. Реализация и проверки завершены 9 октября 2026. Пользователь подтвердил отдельный коммит 9 октября 2026.

CacheService читает параметры непосредственно из env. В server entry остаётся cacheService.initialize() без аргументов; CacheClientConfig и private config удалены. Redis-клиент создаётся и подключается независимо от CACHE_RENDER и CACHE_CRITICAL_CSS. Флаги в SSR middleware отключают чтение и запись кеша.

Render и critical CSS используют обычную строку pending. UUID, привязка к владельцу и передача токенов удалены. Установка pending возвращает boolean; middleware локально сохраняет подтверждение установки.

При чтении render pending запрос сразу выполняет свой SSR без ожидания, polling и повторного SET NX. При отсутствии записи выполняется SET NX; проигранная или неподтверждённая установка также приводит к собственному SSR без публикации. Один подтверждённый запрос публикует результат после ответа. Готовый JSON и pending различаются до JSON-парсера.

Атомарная условная запись сравнивает текущее значение с обычным pending, чтобы не перезаписывать готовую запись и не восстанавливать уже истёкший ключ. Проверки владельца нет. Debug refresh заменяет прочитанную готовую запись на pending через compare-and-set; запрос при уже установленном pending рендерит без публикации.

## Бюджеты и TTL

Все вычислительные бюджеты используют миллисекунды. Настройки обновлены в .env.example, локальном .env, схеме, server, CacheService и critical CSS service.

| Настройка                    | Default  | TTL pending                         |
| ---------------------------- | -------- | ----------------------------------- |
| SSR_RESPONSE_BUDGET_MS       | 30000 мс | Render: бюджет + 1000 мс = 31000 мс |
| CACHE_CRITICAL_CSS_BUDGET_MS | 10000 мс | CSS: бюджет + 1000 мс = 11000 мс    |

Отдельная CACHE_RENDER_BUDGET_MS удалена: TTL render pending вычисляется из общего SSR budget. Значения — положительные целые миллисекунды. Старые BUDGET_SEC больше не читаются. Redis NX и compare-and-set используют PX. TTL готовых записей остаётся в CACHE_RENDER_TTL_SEC и CACHE_CRITICAL_CSS_TTL_SEC; перед PX секунды переводятся в миллисекунды.

## Границы

Пользователь дополнительно согласовал упрощение публикации кеша до обычного SET вместе с пунктом 8; задача сохранена в плане.

Общий SSR deadline ещё не реализован. Здесь введён его параметр и зависимый TTL pending. Пункт 8 отдельно добавит ответ HTTP 500 по истечении 30000 мс, параллельное удаление pending запросом с подтверждённой установкой и запрет поздней публикации. CSS cleanup при ошибке или истечении бюджета входит в пункт 13. Critical CSS рассчитывается после отправки HTML, поэтому его ошибка не меняет уже отправленный HTTP-ответ.

Без токена последовательные установки pending не различаются. Если старый SSR пережил TTL и началось новое вычисление, сравнение строки pending не определяет, к какому вычислению она относится. Запрет публикации просроченного SSR закрывается отдельным пунктом 8; это не проверка владельца.

При чтении pending действует REDIS_READ_TIMEOUT_MS; ожидания чужого рендера нет. Тайм-аут ожидания SET NX/EVAL остаётся пунктом 15. При остановке процесса pending освобождается через TTL.

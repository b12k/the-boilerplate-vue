# Пункт 13: critical CSS в Piscina

База: 56917b6. Статус: реализовано, проверено и подтверждено пользователем 10 октября 2026 для отдельного коммита.

## Изменение

HTTP-процесс отдаёт HTML с обычными стилями, затем отправляет готовую разметку и пути CSS в Piscina 5.3.2. Worker читает CSS и выполняет прежний алгоритм PurgeCSS. Список страниц заранее не нужен. При следующем запросе готовый critical CSS берётся из Redis.

Один worker выполняет один расчёт за раз. Default: один worker, восемь дополнительных заданий и HTML до 1 MiB. Настройки CACHE_CRITICAL_CSS_MAX_THREADS, CACHE_CRITICAL_CSS_MAX_QUEUE и CACHE_CRITICAL_CSS_MAX_HTML_BYTES вынесены в env-defaults.ts; в env-файлах оставлены закомментированные примеры переопределения. Пул создаётся при первом расчёте. Неиспользуемый поток закрывается через 30000 мс.

Общий предел принятых заданий проверяется до передачи HTML в Piscina. Это нужно и для отменяемых заданий: в установленной версии отдельная skipQueue не ограничивается той же проверкой maxQueue, что обычная очередь. Дополнительная очередь приложения не создаётся.

CACHE_CRITICAL_CSS_BUDGET_MS по-прежнему равен 10000 по умолчанию. Он включает ожидание в очереди, запуск worker, чтение файлов и расчёт. При истечении бюджета AbortSignal отменяет задание, а работающий worker прекращается. Поздний результат не публикуется. При ошибке, превышении размера HTML или переполнении пула pending удаляется через существующий DELEX IFEQ. HTTP-ответ уже отправлен; клиент использует полный CSS.

Обычный pending и его TTL budget + 1000 мс сохранены. При pending другой HTTP-запрос сразу продолжает SSR и не запускает дублирующий CSS-расчёт. Принятая CSS-задача не связана с отменой завершённого HTTP-запроса. Graceful shutdown ждёт фоновые задачи, закрывает пул, затем Redis. При превышении общего shutdown budget пул уничтожается вместе с принудительной остановкой сервера.

В development используется .ts worker с тем же SWC loader, что сервер. В production используется собранный .js worker. Worker не импортирует серверный env, Redis или логгер. Knip получает отдельную точку входа для динамически загружаемого worker.

Для небольшого детерминированного CSS во всех режимах проверены три последовательных задания: page-a → page-b → page-a. Результаты совпадают с исходным алгоритмом; лишние селекторы и font-face удаляются, состояние между заданиями не переносится.

Для реальных Home и About результат совпадает побайтно с прежним чтением файлов и PurgeCSS: соответственно 17966 и 15965 байт при полном CSS 30042 байта. Первый ответ содержит обычный stylesheet; следующий содержит critical CSS и подключение полного stylesheet. В neo проверены оба состояния Home: одинаковые основные стили, фон и размер заголовка; горизонтального overflow нет. Screenshot fallback просмотрен.

В изолированном Docker с отдельным Redis пройдены 12 профильных сценариев:

1. Cold → hit: первый ответ отправлен за 29 мс при управляемом расчёте 700 мс; следующий получает CSS.
2. Десять запросов при pending: один CSS-расчёт, ответы не ждут его; максимальный HTTP 31 мс.
3. CPU-расчёт 2500 мс: десять /health завершены за 7 мс, другой SSR — за 7 мс, исходное вычисление ещё работало.
4. Один worker и одно место очереди: третий расчёт пропущен, HTTP 200 и обычные стили, pending очищен; два принятых задания выполнены одним потоком.
5. HTML больше 100 тестовых байт: worker не запущен, pending очищен, HTTP 200.
6. Ошибка worker: pending очищен, следующий запрос успешно пересчитал CSS.
7. CSS budget 700 мс при расчёте 3000 мс: поток прекращён, pending очищен, поздний CSS отсутствует; повторный расчёт успешен.
8. CSS budget 1200 мс включает очередь: второе задание не получает новый полный бюджет после ожидания; pending очищен и позднего результата нет.
9. SIGTERM после отправки HTML: принятое задание закончено и CSS записан до закрытия Redis; exit 0.
10. Shutdown budget 250 мс: принудительная остановка, exit 1, незавершённый CSS не записан. При принудительном выходе pending живёт до своего TTL.
11. Две реплики: один producer, другая немедленно отдаёт HTML; обе затем получают общий CSS.
12. Два workers, MAX_QUEUE=0: два задания работают одновременно в разных потоках, третье пропущено.

Управляемые ошибки, CPU-нагрузка и задержки созданы внешними fixtures. Они проверяют жизненный цикл и изоляцию пула. Расчёты настоящим PurgeCSS проверены отдельно. Fixtures, JSON-результаты и тестовые Redis credentials не добавляются в репозиторий.

## Ограничения

Это проверки поведения, не нагрузочный benchmark и не гарантия RPS. Worker освобождает основной event loop от PurgeCSS, но использует CPU и память того же контейнера. Один worker и очередь из восьми — начальные значения; их нужно измерять на страницах конкретного проекта. Ограничение HTML не является общим лимитом памяти процесса.

На Windows применяется ранее выбранный SWC_NATIVE_BINDING_CACHE. Development выдаёт предупреждение Node о deprecated module.register; функциональные проверки проходят. В старой вкладке после перезапуска dev-сервера наблюдались предупреждения HMR, без ошибок приложения. Production console чистая.

# Тест-план правок

Проверки выполняются после реализации пункта и **до создания его коммита**.
План относится к 35 пунктам из [списка правок](./fixes.ru.md). Номера сценариев совпадают с номерами правок.
Новый тестовый framework и CI этим планом не вводятся.

## Допуск к каждому коммиту

1. Проверить diff: изменён только текущий пункт, отсутствуют временные fixtures, credentials и несвязанные изменения.
2. Для кода, конфигурации и зависимостей выполнить `pnpm check`.
3. Перед каждым коммитом обязательно запускать и проверять приложение во всех трёх режимах: `pnpm dev`, `pnpm start:local` и Docker (свежая сборка образа и запуск контейнера). Проверка одного режима не заменяет остальные. Не проверять новый код старым dist или старым образом.
4. В каждом из трёх режимов выполнить короткий HTTP и браузерный smoke: SSR, hydration, home → about → home и консоль в BrowserOS neo. Проверки текущего пункта и регрессии выбирать по влиянию изменения согласно разделу ниже.
5. Для документации дополнительно выполнить проверку оформления и ссылок. Проверить, что команды запуска соответствуют реально проверенному проекту. Обязательная проверка трёх режимов сохраняется.
6. Закрыть тестовые процессы/контейнеры, восстановить временно изменённые параметры. Выполнить `git diff --check` и проверить финальный diff.
7. Если результат относится к проверяемому изменению и не пройден — исправить и повторить этот сценарий. Ограничение окружения означает «не проверено», а не PASS.
8. Только после проверок передать пользователю diff, результаты и запрос подтверждения/отказа. Сначала пользователь ревьюит изменения; отдельный коммит создаём после явного подтверждения. До подтверждения не коммитим и не начинаем следующий пункт.

Не требуем исправлений ещё не реализованных пунктов. Например, отсутствие версии в health до пункта 14 — исходное поведение, а не блокер пункта 22.
Полную матрицу повторяем, когда изменение затрагивает несколько механизмов; не повторяем все сценарии после косметического изменения.

## Объём проверок по влиянию изменения

Пользователь согласовал сокращённый порядок 8 октября 2026: короткий smoke во всех трёх режимах и проверки текущей правки. Три запуска не отменяются.

- Для каждой правки кода, конфигурации или зависимостей: pnpm check, git diff --check, свежие dev/start:local/Docker и короткий smoke.
- Для серверных правок без влияния на оформление: полный обход мобильных страниц, скролл, анимации и весь набор mock API не повторяем.
- Для UI и CSS: проверяем затронутые страницы и полный применимый UI QA, включая responsive layout, нужные состояния и прокрутку.
- Для store, hydration и prefetch: добавляем сохранение state, pending, failure/retry и отмену, если изменение их затрагивает.
- Для Redis, SSR budgets, Piscina, shutdown и других общих серверных механизмов: профильные проверки отказов, тайм-аутов, параллелизма и нескольких реплик выполняем в отдельном production Docker-окружении. Тот же сценарий не дублируем в других режимах без различий в коде или конфигурации.
- Для различий development/production, путей src/dist, env и сборки: профильные проверки выполняем во всех режимах, на которые влияет изменение.
- Для документации: проверяем оформление, ссылки и команды; дополнительные UI и fault-проверки не запускаем. Короткий smoke трёх режимов сохраняется.

Пройденную проверку без последующего изменения затронутого кода не повторяем. Повтор нужен после исправления ошибки, нового изменения или появления конкретного сомнения. В отчёте фиксируем, какие профильные сценарии выполнены и почему.

## Обязательные режимы запуска

| Режим             | Запуск                                              | Что фиксируем перед коммитом                                                                                                                       |
| ----------------- | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Development       | `pnpm dev`                                          | Запуск, базовый smoke, применимые сценарии, ошибки сервера и браузерной консоли; при изменении UI — обновление страницы после изменения исходников |
| Local production  | `pnpm start:local`                                  | Свежая сборка, запуск, базовый smoke, применимые сценарии, ошибки сервера и браузерной консоли                                                     |
| Docker production | Свежий `docker build` и запуск тестового контейнера | Сборка образа, запуск, базовый smoke, применимые сценарии, ошибки сервера и браузерной консоли                                                     |

Для каждого режима в отчёте указываем команду, результат и ограничения. Режим нельзя пропускать молча или отмечать PASS по результатам другого режима. Если запуск заблокирован окружением, фиксируем «не проверено» и причину; до завершения проверки коммит не считается готовым к ревью. Полный список сценариев повторяем при обоснованном влиянии изменения на общие механизмы, но три режима запуска проверяем всегда.

## Тестовое окружение

- Node и pnpm из настроек проекта, frozen lockfile для проверки зависимостей.
- Production-приложение, отдельный Redis и, при необходимости, две SSR-реплики с общим тестовым Redis.
- Контейнеры и сеть с уникальными именами. Не останавливаем существующий пользовательский Redis и не выполняем FLUSHALL в общем окружении.
- Порты выбираем свободные. Используем только тестовые credentials и тестовый debug key.
- Для fault injection: отдельный TCP proxy, отключение тестового Redis или CLIENT PAUSE внутри отдельного Redis. Разрыв соединения и задержка готового соединения — разные сценарии.
- Медленный upstream, задержанный renderer и тестовые маршруты добавляем только в отдельную тестовую копию/fixture, вне production diff.
- Временные скрипты и результаты храним рядом с этим документом. Старые review-*.mjs можно переиспользовать после адаптации под новые контракты; старые утверждения об ID, query и заголовках обновляем.
- Для браузерных сценариев используем последние стабильные браузеры. Основной smoke — Chromium; изменённые head/CSS/навигацию по возможности также проверяем в Firefox и Safari. Отдельную конфигурацию поддержки браузеров не добавляем; недоступные браузеры явно отмечаем.

## Проверки по пунктам

### 1. Pending SSR render-cache

- CacheService.initialize вызывается без аргументов и читает env напрямую; отдельной config нет. Redis-клиент создаётся и подключается независимо от флагов кеша. При выключенных обоих кешах SSR middleware не вызывает GET/SET/DELEX, SSR остаётся доступен без cache-hit заголовков.
- Холодный ключ: 20 одновременных запросов на один маршрут/device в двух инстансах с общим Redis. Каждый запрос при pending выполняет свой SSR, все ответы корректны. Запрос, получивший подтверждение установки pending, публикует результат, который затем доступен обоим инстансам.
- Медленный первый SSR: запрос с другого инстанса завершает собственный SSR раньше. Pending не вызывает ожидания, polling или повторного SET NX.
- Pending не попадает в JSON-парсер RenderResult и не создаёт 500. Render и CSS pending содержат ровно pending; setPending возвращает boolean.
- Запрос завершился с ошибкой или его процесс остановлен: запись не зависает навсегда; TTL позволяет последующее вычисление.
- После пункта 8 публикация HTML/CSS использует обычный SET с TTL. Только запрос с локальным подтверждением pending публикует результат; просроченный SSR не публикуется. Разные установки pending не различаются по владельцу. Условный переход готовой записи в pending при debug refresh проверяем отдельно.
- Неуспешная/неподтверждённая установка pending: обычный SSR доступен сразу; его результат не публикуется.
- Разные lang/device и разные настроенные маршруты не блокируют друг друга одним pending.
- MS-бюджеты: defaults SSR/CSS 30000/10000, overrides 1234/987, положительные целые числа. Фактический PTTL pending равен соответствующему бюджету плюс 1000 мс: defaults 31000/11000, overrides 2234/1987. TTL готовых HTML/CSS сохраняет секунды. Critical CSS budget 50 мс прерывает контролируемое чтение длительностью 120 мс около заданного предела.

Результаты 9 октября 2026: [ревью пункта 1](./fix-1-review.ru.md). Проверяем короткий smoke dev/start:local/Docker; профильные concurrency/pending/TTL/Redis-сценарии выполняем в отдельном Docker-окружении. Ожидание pending и токены исключены по уточнению пользователя.

### 2. Request ID

- Два запроса без ID, включая cold и hit: разные непустые X-Request-ID.
- Запрос с клиентским ID: возвращается тот же ID и с ним связан серверный лог.
- Пустой клиентский ID: генерируется новый UUID. Изменение только ID не вызывает patch одинакового cached context.
- У разных инстансов и параллельных запросов без клиентского ID нет повторного использования ID из кеша.
- В window.INITIAL_STATE, state.context.cached и Redis RenderResult Request ID отсутствует.
- 404, 500, redirect и health получают ID текущего запроса после применения общей политики.
- Статические ресурсы и development live reload также получают ID; logger выполняется до обработчиков ответа.

### 3. Общий CACHE_SALT

- Production: обе категории используют VERSION из package.json и разные префиксы [RENDER]/[CRITICAL-CSS].
- При версии A запись не видна процессу версии B. Проверяем на двух тестовых package.json/образах, не меняя рабочий package.json для теста.
- Development: соль стабильна в одном процессе и меняется после перезапуска.
- Старые переменные не являются обязательными и не управляют солью.

### 4. Redis connection retries

- Недоступен при старте: число попыток ограничено, после завершения цикла приложение работает без кеша.
- Проверяем значение по умолчанию 5 и явные значения 2 и 0. При старте ожидаем соответственно 6, 3 и 1 подключение; после потери ready-соединения — максимум 5, 2 и 0 попыток восстановления. Проверяем схему в source и dist: отрицательное, дробное и нечисловое значение отклоняются.
- Разрыв уже установленного соединения: та же ограниченная политика восстановления; HTTP не ждёт reconnect loop.
- Redis восстановлен до исчерпания попыток: render и critical CSS снова работают. Повторный обрыв проверяет восстановление бюджета после успешного подключения.
- Проверяем отказ TCP, ошибку AUTH и peer, который принимает TCP, читает handshake, но не отвечает. Вся попытка, включая handshake, ограничена 1000 мс; между неудачными попытками пауза 1000 мс. Для тихого peer допускаем 900–1600 мс по измерениям proxy; после завершения нет открытых клиентских сокетов.
- Успешное ready-соединение остаётся открытым после истечения 1000 мс: connection watchdog отменён, а не работает как тайм-аут idle-сокета.
- После исчерпания попыток нет бесконечного цикла и unhandled rejection, SSR доступен. Возвращение Redis после исчерпания не запускает новый цикл без перезапуска приложения.

### 5. Redis GET timeout

- Проверяем REDIS_READ_TIMEOUT_MS в source и dist: default 1000, явные 250/1000/1500; 0, отрицательное, дробное, нечисловое и пустое значение отклоняются. В отдельном Docker проверяем реальное изменение срока GET и передачу настройки env → server → CacheService → RedisCache.
- Redis подключён и ready, но ответ GET задержан на 1500–3000 мс: ожидание операции завершается примерно за 1000 мс, SSR продолжается, тайм-аут залогирован.
- Измеряем время Redis-операции отдельно от полного HTTP: весь ответ может занять больше секунды из-за SSR.
- Допуск времени заранее фиксируем под среду, например ±250 мс на свободном тестовом хосте.
- Для профильной проверки пункта 5 фиксируем 900–1250 мс на RedisCache.get. HTTP при одном тайм-ауте включает также обычный SSR; при двух последовательных чтениях проверяем два тайм-аута и около 2000 мс ожидания.
- При REDIS_READ_TIMEOUT_MS=250 ожидаем промах GET за 200–500 мс; при 1500 ответ, задержанный на 1100 мс, должен быть получен успешно. Логи содержат настроенный предел. Первоначальный тайм-аут подключения остаётся отдельным механизмом.
- Ответ быстрее лимита используется. Поздний ответ не меняет уже выбранный результат и не отправляет второй HTTP-ответ.
- Запоздалая ошибка обработана; соседний запрос через то же соединение не обрывается из-за глобального destroy.
- Десять одновременно задержанных GET завершаются промахами в пределах бюджета каждого; после получения поздних ответов тот же клиент успешно читает следующий ключ. Быстрое чтение не оставляет watchdog, который позже логирует ложный тайм-аут.
- Для render и critical CSS отдельно проверяем HTTP 200, отсутствие соответствующих cache-hit заголовков и дальнейшее восстановление hits через то же соединение. При промахе critical CSS основной stylesheet присутствует в HTML.

### 6. SSR assets snapshot

- Production: повторные и одновременные загрузки используют один snapshot; чтения неизменяемых файлов не растут с числом запросов.
- Холодный старт читает необходимые файлы, рендер работает. SSR manifest для dev decache не требуется в production.
- Development: изменение компонента и повторная сборка видны в следующем SSR без перезапуска процесса.
- Первоначальная ошибка чтения не оставляет навсегда rejected snapshot.
- Diff этого пункта ограничен ssr-assets.service.ts.

Результаты 9 октября 2026: [ревью пункта 6](./fix-6-review.ru.md). Короткий HTTP/browser smoke пройден в dev, свежем start:local и свежем Docker. В отдельном production probe проверены 20 одновременных и 20 повторных загрузок: один read клиентского manifest, ноль reads SSR manifest. Ошибки ENOENT клиентского manifest, JSON parse и отсутствующего renderer допускают повторную попытку. Dev probe проверяет обновление manifest, renderer и CommonJS-зависимости. Отдельная реальная dev-сборка компонента в builder-контейнере подтверждает изменение и восстановление HTML без перезапуска процесса. Fixtures остаются вне репозитория.

### 7. Удаление LRU

- В исходниках и lockfile больше нет прямой зависимости/реализации LRU для серверного кеша.
- REDIS_URL вычисляется в env.ts из обязательных REDIS_HOST, REDIS_PORT и REDIS_PASSWORD; входной REDIS_URL больше не управляет конфигурацией. Проверяем отсутствие обязательных полей, заданные host/port, пустой пароль и корректное кодирование спецсимволов.
- Уточнение пользователя 9 октября: CACHE_RENDER=false и CACHE_CRITICAL_CSS=false отключают операции кеша в middleware; Redis-клиент всё равно создаётся и подключается. При недоступном Redis SSR остаётся доступен, действует ограниченный reconnect loop.
- Redis недоступен: приложение запускается/восстанавливает HTTP после ограниченного подключения и отдаёт SSR, без памяти как fallback-кеша.
- Redis работает: cold/hit для обоих кешей; CACHE_RENDER и CACHE_CRITICAL_CSS можно включать независимо.

### 8. SSR response budget

- Упрощение кеш-сервиса: публикация render/CSS выполняется через SET с TTL без Lua-проверки pending; SET NX, локальный флаг и запрет поздней публикации сохраняются.

- Через fixture задержать асинхронный prefetch/renderer сверх бюджета: один ответ 500 через обычный error middleware, процесс остаётся жив. Текст страницы ошибки меняется пунктом 29.
- Проверить configurable короткий бюджет для теста и значение по умолчанию 30000 мс; время ответа считать с входа в SSR middleware.
- Успешный запрос ниже лимита отвечает нормально; таймер не срабатывает после завершения.
- После тайм-аута renderer поздно завершается/отклоняется: нет второго send, ERR_HTTP_HEADERS_SENT, unhandled rejection и поздней записи результата в кеш.
- Тайм-аут запроса с подтверждённым pending запускает его удаление без ожидания Redis; готовая запись не удаляется. Запрос без собственного подтверждения pending не удаляет его.
- Отдельно проверяем бюджет, включающий чтение Redis; чужой pending не вызывает ожидания. Синхронную CPU-блокировку не считаем прерываемой таймером.

### 10. Graceful shutdown

- SIGTERM и SIGINT: активный HTTP/SSR завершается в пределах бюджета, новый трафик не принимается, процесс завершает работу.
- Повторный сигнал не запускает второе закрытие ресурсов.
- Ответ уже отправлен, но CSS/job ещё выполняется: shutdown учитывает фоновую работу.
- После HTTP deadline рендер игнорирует AbortSignal и продолжает работу: shutdown ждёт исходный Promise, а не только уже завершившееся HTTP middleware.
- Нет ошибок записи в уже закрытый Redis при нормальном drain. Завершение Piscina до Redis проверяем после добавления пула в пункте 13.
- Зависшая задача: по общему бюджету 30 секунд принудительное завершение с ненулевым кодом. Для быстрого сценария можно использовать короткий настроенный бюджет.
- Startup с отсутствующим SSR asset: сервис не начинает принимать трафик; без ручного shape-validation.
- Redis недоступен: /health остаётся ready, SSR работает; shutdown отменяет retries и handshake. Проверяем close/destroy во время handshake и непосредственно после запуска connect, до TCP-соединения: поздний сокет не удерживает процесс.
- Новый запрос по ещё открытому HTTP-соединению во время drain получает 503; /health возвращает ready=false и status=DRAINING.
- SHUTDOWN_BUDGET_MS: default 30000, override 250; ноль, отрицательное, дробное, нечисловое и пустое значение отклоняются. Проверяем source и dist.
- Docker stop с достаточным внешним grace period проверяем отдельно от прямого process signal.

### 11. DEBUG

- Development: диагностика включена из режима без DEBUG в env-файлах.
- Production без ключа: обычный HTML, диагностики нет, запуск успешен. Пустое или невалидное заданное значение отклоняется при запуске и в development, и в production.
- Production с верным тестовым ключом: полная диагностика доступна. Неверный/отсутствующий ключ её не включает.
- Проверяем cookie, header и query. DEBUG из окружения игнорируется: false не отключает development-диагностику, true не включает production-диагностику без ключа.
- Последовательные debug и обычные запросы, в том числе cache hit: диагностический режим текущего запроса не переносится другому клиенту.
- Первый запрос по холодному render-cache содержит правильный ключ в query; следующий обычный запрос получает cache hit без ключа в HTML, context.query, context.url и context.cached. Остальные query-параметры сохраняются.
- Неверный ключ не разрешает ENV_OVERRIDES. Верный ключ с недоступным тестовым API даёт диагностический 500; следующий обычный запрос снова получает обычный 200 без overrides.

### 12. Log redaction

- Передаём уникальные тестовые секреты через Authorization, cookies, credentials, debug key, вложенные поля, URL и сообщения ошибок.
- В захваченном stdout/stderr нет исходных значений секретов; остаются полезные operation, Request ID и описание ошибки.
- Проверяем plain message и Error со stack, а не только JSON-объект с очевидным password-полем.
- По верному debug key разрешённая полная HTML-диагностика сохраняется.
- Проверяем production JSON и development pino-pretty для source, local dist и Docker dist. Child bindings, массивы и секреты в именах вложенных полей не обходят маскирование.

### 13. Piscina critical CSS

- Холодный CSS: первый ответ не ждёт вычисления, последующий использует записанный critical CSS.
- При управляемой тяжёлой CSS-задаче основной процесс продолжает обслуживать /health и другие запросы; сборка CSS выполняется в worker.
- Число worker/задач и очередь соответствуют лимитам. При переполнении/слишком большом HTML HTTP продолжает работать с обычными стилями.
- Проверяем общий предел принятых задач, включая отменяемую очередь Piscina. Один worker выполняет задачи последовательно; два workers действительно работают параллельно. Значение MAX_QUEUE=0 не оставляет дополнительной очереди.
- Две реплики с общим Redis: только одна ставит pending и запускает расчёт; другая сразу отдаёт HTML и затем использует общий результат.
- Ошибка worker или превышение бюджета: pending удаляется, поздний результат не публикуется, unhandled rejection отсутствует.
- Бюджет начинается при принятии задания и включает очередь и запуск потока. Тайм-аут работающего задания прекращает worker; после ошибки/отмены пул принимает следующее задание.
- Завершение запроса не отменяет уже принятую фоновую задачу; shutdown завершает её по своей политике.
- Сравниваем CSS для детерминированной страницы до/после переноса и визуальную корректность с CSS и без него.
- Проверяем настоящую загрузку .ts worker через SWC в development и .js worker в local/Docker production. Defaults и валидные/невалидные overrides проверяем для каждой формы серверной схемы.
- Актуальные результаты: [пункт 13](./fix-13-review.ru.md). Сценарии ошибок и управляемой CPU-нагрузки используют внешние fixtures; реальные Home/About отдельно проверяем с неизменённым PurgeCSS.

### 14. Health

- GET /health: JSON, текущая version, готовность, 200 и no-store.
- Query и стандартный trailing slash не меняют контракт. Вложенный /health/... и POST/PUT/PATCH/DELETE на готовом сервере не попадают в health-обработчик. Автоматический HEAD от Express сохранён: статус и заголовки GET, пустое тело, без отдельного обработчика.
- В startup/draining готовность false; если HTTP ещё доступен на существующем соединении — 503. После закрытия listener новое соединение может быть отклонено, а не получить 503.
- Недоступный Redis при работающем SSR не меняет health на ошибку.
- Проверка не вызывает renderer и не выполняет Redis-команд.
- Отдельные /ready и /version не регистрируются как новые служебные маршруты.
- Проверяем состояния STARTING/OK/DRAINING через настоящий health middleware для source, local dist и Docker dist; на работающем сервере — routing, заголовки и общую версию из package.json.
- Изоляция: серия /health не меняет Redis commandstats и не вызывает renderer fixture. Отдельно проверяем настоящий HTTP pipeline во время shutdown и готовность при недоступном Redis. Результаты: [пункт 14](./fix-14-review.ru.md).

### 15. SET/DELEX timeouts

- Готовое соединение с задержанными SET, SET NX/IFEQ и DELEX IFEQ: ожидание каждого ограничено одной секундой, результат не считается подтверждённым.
- При неподтверждённой установке pending выполняем SSR без публикации результата.
- Поздний успех SET возможен, но не приводит к второму ответу. SET NX не заменяет существующую запись; SET IFEQ для debug refresh меняет только прочитанное значение на pending; DELEX IFEQ удаляет только совпадающий pending.
- Быстрые команды и ответы до 1000 мс сохраняют значения, EX/PX TTL и не оставляют таймер ложного тайм-аута. GET сохраняет отдельный REDIS_READ_TIMEOUT_MS.
- В отдельном Redis CLIENT PAUSE WRITE задерживает реальные SET/NX/IFEQ/DELEX. Вторая fixture моделирует позднюю ошибку и Promise без подтверждения. Общий Redis-клиент остаётся ready.
- Поздняя ошибка наблюдается; ожидание кеша завершается даже для Promise без ответа. Общий graceful shutdown проверяется в пункте 10.
- При задержке event loop результат после бюджета не считается подтверждённым; синхронную блокировку таймер прервать не может.
- Не добавляем тестовое требование нового лимита числа outstanding commands — это не согласованная правка.

### 16. Pathname matcher

- /en, /en?foo=1 и /en?foo=2: один ключ при одинаковом device type; повторные запросы используют его.
- /de и другой device type дают другой ключ.
- /en/about, не включённый в текущий idempotency config, не начинает кешироваться из-за изменения matcher.
- Query остаётся в Context текущего запроса. Тестовая кешируемая страница не зависит от query: не проверяем ложное обещание корректности query-dependent HTML с общим ключом.

### 17. Resources текущей страницы

- Fixtures: маршрут A с уникальными JS/CSS, маршрут B с другими ресурсами, общий layout и общий CSS.
- Raw HTML A содержит initial + A + shared, но не prefetch ресурсов B. Нет повторов; порядок CSS сохраняется.
- Браузер на холодном кеше корректно отображает A, затем загружает B при навигации. Все используемые чанки отвечают успешно.
- Повторный SSR из Redis сохраняет mapping использованных компонентов и корректные стили.
- Critical CSS есть/нет, JavaScript выключен: необходимые полные стили доступны во всех трёх сценариях.
- Две ленивые страницы с разной разметкой позволяют обнаружить потерю CSS; одной home для проверки недостаточно.
- Отдельный defineAsyncComponent со scoped CSS должен присутствовать в SSR и получать собственные CSS/JS. Scope ID серверного HTML совпадает с селекторами клиентской сборки; проверяем computed styles, а не только HTTP 200.
- Идентификаторы использованных компонентов хранятся в RenderResult/Redis; в Pinia и window.INITIAL_STATE их нет. Setup и prefetch продолжают работать.
- Состав ресурсов проверяем при CSS miss, hit, pending и выключенном кеше. Browser resource timing показывает загрузку уникальных ресурсов соседнего маршрута после навигации.
- Проверку без JavaScript выполняем в production local/Docker. В development действует vue-style-loader; проверяем стили после hydration и отсутствие ошибок lazy compilation.
- INITIAL_STATE и переключение async CSS расположены перед закрывающим body. При присваивании состояния SSR-разметка уже существует, hydration ещё не началась; после запуска клиента все data-async-css имеют rel=stylesheet. Nonce и noscript fallback сохраняются.

### 19. HTTP methods

- GET HTML — обычный SSR. HEAD — тот же статус/заголовки без тела, автоматическое поведение Express.
- POST/PUT/PATCH/DELETE/OPTIONS на HTML-маршруте — 405, Allow: GET, HEAD, renderer не выполняется. Проверяем корень языка, trailing slash, вложенный путь и query.
- HEAD для успешной страницы и SSR 404 сохраняет статус и Content-Type GET, имеет пустое тело и собственный X-Request-ID.
- Зарегистрированная POST API fixture перед SSR не попадает под запрет HTML methods, включая API внутри языкового префикса. Отдельный renderer fixture подтверждает отсутствие вызовов для 405 и API; контрольные GET/HEAD действительно запускают renderer.
- Похожие префиксы /english и /enough, а также неподдерживаемый язык не получают SSR 405: сохраняется обычный 404.
- Языковой redirect и health сохраняют согласованные маршруты.

### 20. Cache headers

- HTML miss/hit, debug, 404, 500 и health: no-store.
- Хешированные JS/CSS/изображения: public, max-age=31536000, immutable.
- Manifest: no-store; unhashed favicon: no-cache. Проверяем фактический ответ, а не только параметры serveStatic.
- В development основной сервер отдаёт static с no-cache; временные чанки и manifest на отдельном Rspack dev server получают no-store.
- GET, HEAD, query и условный запрос для static сохраняют Cache-Control. Favicon и unhashed static дают 304 при совпадающем Last-Modified; HEAD и 304 имеют пустое тело.
- Ошибка после назначения static cache header, отсутствующий файл, SSR timeout, debug и readiness 503 возвращают no-store. Missing hashed asset не получает immutable.
- Разрешённые source maps сохраняют private, no-store, в том числе путь с .map и хешем. HTML-файл с хешем получает no-store. Range 206 для hashed static сохраняет immutable, ошибочный Range 416 — no-store.
- Политика cache-control действует на early responses и redirects, где это предусмотрено. TTL Redis не превращается в TTL HTML.
- Версионная полная перезагрузка действительно получает новый HTML.

### 21. Security headers

- /health, /, favicon, API, public asset, manifest, source-map rejection, SSR, 404, 405, 500 и readiness 503: общие headers присутствуют, X-Powered-By отсутствует. HSTS включён только в production.
- HTML: корректная CSP; nonce в разрешённых inline scripts совпадает с nonce заголовка текущего ответа.
- Два ответа из render-cache не переиспользуют nonce первого запроса.
- Static не требует HTML nonce. Development HMR/live reload и production hydration не блокируются CSP.
- Ранняя ошибка до SSR получает HTML CSP и nonce; debug scripts используют тот же nonce. JSON, static, source maps и SSE не создают HTML nonce. Автоматический HEAD сохраняет заголовки GET и пустое тело.

### 23. 500 message

- Управляемая ошибка SSR: HTTP 500 и видимый текст Unable to load the page. Please try again later.

### 25. Redirect

- Fixture /old → /new: HTTP 302 и Location с языковым base, без SSR page; meta.responseCode=301 меняет код на 301.
- Код берём из redirectedFrom.meta.responseCode ?? 302; responseCode=200 целевой страницы не отменяет обычный HTTP redirect. У CatchNotFound явно задан responseCode=404 для сохранения внутреннего перехода.
- Redirect с query и цепочкой переходов: Location указывает конечный адрес, query сохраняется согласно Vue Router.
- Prefetch, renderer HTML и CSS worker целевой страницы не запускаются для redirect-ответа; redirect не записывается в render-cache.
- Если запрос захватил render pending, redirect удаляет его; следующий запрос снова может захватить ключ. Проверяем на отдельном Redis.
- Проверка 301/302/303/307/308 не считает 304 редиректом.
- Обычный page использует meta.responseCode ?? 200. /en/missing остаётся 404 с клиентской навигацией; серверный fallback JS-переход сохранён.
- SSR-redirect и переход по той же ссылке в клиентском приложении приводят к одному целевому маршруту.


Не сохраняем все HTML/log payload по умолчанию. Для доказательства достаточно проверяемых статусов, заголовков, результатов утверждений и измерений; screenshot нужен для визуального изменения.

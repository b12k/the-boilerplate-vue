## Список

### 1. Pending для SSR render-cache

CacheService читает настройки непосредственно из env; initialize вызывается без аргументов. Redis-клиент создаётся и подключается всегда; флаги кеша отключают его чтение и запись в SSR middleware.
Render и critical CSS используют обычное значение pending без UUID и привязки к владельцу. Запрос локально сохраняет подтверждение установки pending; только этот запрос публикует свой результат.
Различаем отсутствие записи, pending и готовый RenderResult. Pending не передаём в JSON-парсер готового результата.
Пользователь уточнил контракт 9 октября: при pending сразу выполняем собственный SSR без ожидания, polling и повторного захвата. При проигранном или неподтверждённом захвате также выполняем SSR. Такой результат отдаём клиенту без записи в кеш.
Параллельные SSR разрешены. Отказ Redis не блокирует обычный SSR.
Все вычислительные бюджеты задаём в миллисекундах. SSR_RESPONSE_BUDGET_MS по умолчанию 30000 задаёт общий SSR budget; CACHE_CRITICAL_CSS_BUDGET_MS по умолчанию 10000 — CSS budget. TTL pending вычисляется как соответствующий бюджет плюс 1000 мс: 31000 мс для render и 11000 мс для CSS. Отдельной настройки render pending budget нет. Pending использует Redis PX. TTL готовых записей остаётся в CACHE_RENDER_TTL_SEC и CACHE_CRITICAL_CSS_TTL_SEC. Сам HTTP deadline и удаление pending при тайм-ауте реализуются отдельным пунктом 8.

### 2. Request ID вне сериализуемого контекста

Удаляем Request ID из Context, Pinia state и данных render-cache, включая вложенный сохранённый контекст. Сохраняем его в запросе и логах.
Принимаем ID клиента; если его нет, генерируем. Для каждого ответа устанавливаем X-Request-ID текущего запроса, в том числе при попадании в кеш.
При переданном клиентом ID сервер возвращает его: уникальность в этом случае определяется клиентом.

### 3. Общий CACHE_SALT

Убираем CACHE_RENDER_SALT и CACHE_CRITICAL_CSS_SALT из env-файлов и схемы. CACHE_SALT вычисляем в env.ts: версия приложения в production, время запуска в development.
Сохраняем разные пространства ключей render и critical CSS. Каждому релизу соответствует новая версия package.json.

### 4. Ограниченные попытки подключения Redis

Добавляем REDIS_CONNECTION_RETRIES со значением по умолчанию 5. После исчерпания попыток приложение продолжает SSR без кеша и логирует недоступность.
HTTP-запросы не ждут цикла переподключения. Чтение возвращает промах, захват pending — false, запись пропускается.
REDIS_CONNECTION_RETRIES задаёт число повторных попыток: при старте одна первоначальная плюс N повторных, после потери ready-соединения — до N попыток восстановления. Ноль оставляет только первоначальное подключение. Успешное подключение восстанавливает бюджет следующего обрыва.
Каждая попытка ограничена 1000 мс, включая TCP и Redis handshake. Между неудачными попытками пауза 1000 мс. После исчерпания фонового цикла новых попыток нет до перезапуска процесса; SSR остаётся доступен.

### 5. Тайм-аут чтения Redis: REDIS_READ_TIMEOUT_MS

Добавляем необязательный REDIS_READ_TIMEOUT_MS со значением по умолчанию 1000: положительное целое число миллисекунд. Пользователь согласовал настройку 9 октября. Передаём её из env через CacheService в RedisCache.
Применяем к чтению render-cache и critical CSS. После истечения настроенного бюджета прекращаем ожидание, считаем промахом, продолжаем SSR и логируем тайм-аут с фактическим пределом.
Поздний результат не используется, позднее отклонение Promise обрабатывается. Один тайм-аут не уничтожает общее соединение Redis.
Это предел ожидания, а не гарантия отмены уже отправленной команды.
Лимит применяется отдельно к каждому GET. Текущий SSR читает render и critical CSS последовательно; два тайм-аута могут добавить два бюджета чтения, по умолчанию около двух секунд. Общий response budget относится к пункту 8.

### 6. SSR assets в памяти

Изменения этого пункта ограничены файлом src/server/services/ssr-assets.service.ts.
В production переиспользуем загруженный snapshot manifest/render и объединяем одновременную первоначальную загрузку.
SSR manifest для development decache не читаем в production без необходимости. Development сохраняет актуализацию assets.
Не сохраняем неуспешную загрузку как постоянный результат.

### 7. Удаление серверного LRU

Удаляем реализацию, fallback и зависимость lru-cache. Redis — единственный backend кеша.
REDIS_URL вычисляем в env.ts из обязательных REDIS_HOST, REDIS_PORT и REDIS_PASSWORD. Пользователь изменил контракт 8 октября: отдельный входной REDIS_URL и условную проверку его обязательности удаляем; Redis-параметры переносим в Required. Пустой пароль означает URL без credentials. Пароль со спецсимволами кодируем.
Уточнение пользователя 9 октября: Redis-клиент создаётся и подключается независимо от флагов кеша; при отключённых кешах middleware пропускает чтение и запись.
Недоступный Redis при корректной конфигурации означает SSR без кеша, а не падение приложения.

### 8. SSR response budget: 30 секунд

Используем SSR_RESPONSE_BUDGET_MS со значением по умолчанию 30000, введённую в пункте 1. Бюджет начинается в SSR middleware и включает ожидание кеша, prefetch и рендер.
При превышении возвращаем HTTP 500 с обычной страницей ошибки; логируем SSR_RESPONSE_TIMEOUT, ID, маршрут и длительность.
Процесс продолжает работать. Запрос, подтвердивший установку pending, при тайм-ауте параллельно запускает удаление pending; ответ 500 не ждёт Redis. Удаляем только значение pending, чтобы не удалить готовую запись. Не отправляем поздний ответ и не кешируем результат просроченного SSR. Чистим таймеры и обрабатываем поздние ошибки.
Вместе с deadline упрощаем CacheService: публикация готового render/CSS использует обычный SET с TTL вместо Lua-сравнения с pending. SET NX и локальное подтверждение установки pending сохраняем; поздний результат не допускаем к публикации. Условное обновление ранее прочитанной готовой записи для debug refresh рассматриваем отдельно от публикации.
По запросу пользователя 9 октября обновляем Redis до 8.10.2 и закрепляем redis:8.10.2-alpine в Compose. Встроенные SET IFEQ и DELEX IFEQ заменяют Lua для debug refresh и очистки pending. Требуется Redis >= 8.4; node-redis 6.3.0 уже поддерживает команды. Существующий volume сохраняем.
Таймер не может прервать синхронный JavaScript; отмена поддерживаемых асинхронных операций — пункт 9.

### 9. Централизованная отмена SSR API-запросов

Отдельный коммит от response budget. Создаём AbortController в SSR middleware и передаём сигнал через renderer/createApp в createApi.
Базовый сигнал автоматически применяется к запросам API. Дополнительный сигнал prefetch объединяется с ним.
Истечение бюджета и отключение клиента отменяют поддерживаемые операции. Сигнал не сериализуется в Context или store.
После prefetch проверяем отмену до продолжения SSR. Нормальное завершение HTTP не отменяет API-сигнал; таймер response budget имеет отдельный контроллер. При закрытом клиентском соединении повторный ответ не отправляем, подтверждённый pending очищаем. Глобальную отмену клиентского приложения этим пунктом не вводим.

Проверки SSR-операций централизуем в utility execInSsrOrAbort, экспортируемой через @app/utils: callback и ssrAbortSignal, проверка отмены перед запуском и после завершения операции. Renderer применяет её к createApp/prefetch/renderToString; utility доступна для других SSR-операций.

Замечания ревью 10 октября: используем явные имена сигналов и createSsrResponseBudget. createServices(context, logger, ssrAbortSignal?) передаёт входы фабрикам; каждая фабрика конфигурирует сервис сама. API_URL из .env попадает в context.apiUrl; createApi использует этот полный адрес для Axios и в SSR, и в браузере. apiConfig и ssrApiOrigin отсутствуют. Моки перенесены на сервер в /api/mocks; примеры выполняют настоящий HTTP. Store и страницы не передают сигналы: SSR-сигнал задан клиенту Axios, клиентский navigation signal обновляется router. Дополнительный per-call signal объединяется с SSR-сигналом через interceptor. [Контракт API](../api.md).

Удаляем общий X-Cache и cacheType, сохраняем заголовки конкретных cache hits. Promise-правила с повторяющимися suppress-комментариями выключаем в общем конфиге; max-params оставляем 4 без исключений для файлов. Функции кеша с четырьмя параметрами переводим на объекты. Общий [список неоднозначных имён](./naming-review.ru.md) подготовлен для отдельного ревью.

### 10. Graceful shutdown

Выносим управление shutdown в utility. Обрабатываем SIGTERM/SIGINT один раз; отмечаем draining и прекращаем принимать новые запросы.
В рамках SHUTDOWN_BUDGET_MS (по умолчанию 30000) ждём HTTP, активный SSR и фоновые задания, включая рендер, который продолжает выполняться после HTTP deadline. Завершаем Piscina до закрытия Redis; сам пул добавляется пунктом 13.
По исчерпании бюджета принудительно закрываем ресурсы и завершаем процесс с кодом ошибки.
До начала приёма запросов вызываем await loadSsrAssets() и в development, и в production. Ручную проверку формы manifest не добавляем.
Состояние готовности используем в единственном /health. Отказ необязательного кеша не делает SSR-сервис неготовым.
При закрытии Redis отменяем handshake и паузы reconnect; TCP-соединение, завершившее подключение после destroy(), также закрываем.

### 11. DEBUG из режима приложения

Удаляем DEBUG из .env, .env.example, env-defaults.ts и схемы. В env.ts DEBUG вычисляется как !IS_PROD.
DEBUG_ON_KEY остаётся опциональным UUID; отсутствие переменной выключает доступ по ключу. Пустое или невалидное заданное значение отклоняется схемой.
Правильный ключ позволяет включить production-диагностику. Полная HTML-диагностика для доверенного разработчика сохраняется.
Проверяем ключ по исходному запросу, затем исключаем DEBUG_ON_KEY из сериализуемых context.query и context.url. Остальные query-параметры сохраняем. Ключ не должен попадать в обычный ответ через context.cached после debug-запроса на холодном кеше.
Автоматическую ротацию ключа не реализуем: она относится к эксплуатации.

### 12. Маскирование секретов в логах

Маскируем поля с credentials, токенами, cookies, Authorization и DEBUG_ON_KEY, а также известные секреты в URL и текстовых сообщениях/ошибках.
Проверяем, что вложенные объекты и Request ID не обходят политику логирования секретов.
Очистка выполняется через Pino hooks.streamWrite после сериализации и до JSON/pretty-вывода. Общая utility обрабатывает вложенные объекты, массивы, child bindings, сообщения и Error/stack без изменения исходных объектов. Известные секреты берём из REDIS_PASSWORD, DEBUG_ON_KEY и credentials/чувствительных query-параметров настроенных API_URL/REDIS_URL; учитываем URL encoding. При ошибке очистки выводим безопасное сообщение без исходного содержимого.
HTML-диагностику по доверенному ключу не маскируем. Универсальное распознавание произвольных неизвестных секретов не обещаем.

### 13. Critical CSS в Piscina

Расчёт по фактически отрендеренному HTML выполняется после ответа в ограниченном пуле потоков. Предварительный список страниц не нужен.
Сохраняем обычный pending без токена, TTL с запасом 1000 мс и локальное подтверждение установки pending. При ошибке или тайм-ауте расчёта удаляем pending; поздний CSS не публикуем. Ограничиваем потоки, очередь, размер задания и бюджет, включая ожидание в очереди.
При перегрузе или ошибке пропускаем оптимизацию и логируем. Страница получает необходимые обычные стили независимо от critical CSS.
Принятое фоновое задание имеет собственный жизненный цикл. Shutdown завершает пул до Redis в общем бюджете.
Начальные defaults: CACHE_CRITICAL_CSS_MAX_THREADS=1, CACHE_CRITICAL_CSS_MAX_QUEUE=8, CACHE_CRITICAL_CSS_MAX_HTML_BYTES=1048576. Предел одновременно принятых задач равен threads + queue. Настройки переопределяются через env; их подбираем под CPU и память контейнера после замеров реальных страниц. Бюджет CACHE_CRITICAL_CSS_BUDGET_MS по-прежнему равен 10000 по умолчанию. Неиспользуемый worker завершается через 30000 мс; выключенный CSS-кеш не создаёт пул.

### 14. Единственный GET /health

Возвращаем JSON с состоянием готовности и версией приложения из общего VERSION. Ответ не кешируется.
Готовый сервер отвечает 200; запускающийся или draining — 503, если ещё принимает соединения.
Не выполняем SSR и Redis-запросы внутри проверки. Отдельные /ready и /version не добавляем.
Этот контракт отражает готовность принимать трафик; правила автоматического перезапуска инфраструктуры задаются отдельно.

### 15. Тайм-аут остальных Redis-операций: 1000 мс

Ограничиваем ожидание SET HTML/CSS, захвата pending через SET NX, условного debug refresh через SET IFEQ и удаления pending через DELEX IFEQ.
При тайм-ауте логируем неподтверждённую операцию. При неподтверждённой установке pending результат не публикуем.
Поздние результаты и ошибки обрабатываем. Уже отправленная запись может выполниться после тайм-аута.
Отдельный лимит числа незавершённых Redis-команд не включён в согласованный объём.

### 16. Pathname в idempotency matcher

Передаём только pathname вместо URL с query. /en, /en?foo=1 и /en?foo=2 используют один ключ при одинаковом device type.
Query остаётся в Context. Только явно настроенные маршруты участвуют в render-cache.
Договорённость проекта: query не меняет кешируемый HTML этих маршрутов. Автоматического bypass для query не добавляем.

### 17. Assets текущей SSR-страницы

Добавляем build-сопоставление компонентов с CSS/JS-ресурсами, включая общие зависимости и порядок CSS.
Автоматически собираем используемые компоненты через SSR context. Их идентификаторы входят в RenderResult и render-cache, но не в Pinia.
Подключаем initial и используемые текущей страницей ресурсы. Без critical CSS — обычные stylesheet; с critical CSS — асинхронное подключение; noscript получает нужные стили страницы.
Убираем blanket prefetch всех async-чанков. Чанки других маршрутов загружаются при навигации.
Проверяем результат после кешированного SSR и на маршруте с lazy-компонентом.

### 18. Клиентский сервис версии и восстановления чанков

Сравниваем исходную версию из клиентского Context с версией /health. При различии перезагружаем страницу.
Сервис инкапсулирует start/stop/check и обработку ошибок загрузки JS/CSS-чанков. Подключается только на клиенте.
Polling без перекрывающихся запросов, при скрытой вкладке пауза, при возвращении проверка. Ошибка чанка запускает внеочередную проверку версии.
При подтверждённой новой версии переходим на нужный URL полностью. Ошибка health не вызывает перезагрузку. Предусматриваем защиту от цикла перезагрузок.
Начальные ориентиры: интервал около 60 секунд с jitter, тайм-аут проверки 3 секунды. Конкретные параметры проверяем при реализации.
Релиз переключается целиком, не rolling. Сервис не может восстановить начальный JS, если он не загрузился и сам сервис ещё не запущен.

### 19. HTTP methods для SSR

Регистрируем SSR как GET. Автоматическая обработка HEAD в Express сохраняется без отдельной логики.
Другие методы на HTML-маршрутах получают 405 с Allow: GET, HEAD. Служебные и API-маршруты обрабатываются до этого ограничения.

### 20. HTTP cache policy

HTML, диагностика, ошибки и health: Cache-Control: no-store.
Статические ресурсы с content hash: public, max-age=31536000, immutable.
Manifest: no-store. Статические файлы без хеша, например favicon: no-cache с повторной проверкой.
TTL Redis остаётся политикой внутреннего кеша и не переносится в HTTP TTL HTML. Дополнительный заголовок Redis TTL не добавляем.

### 21. Единые security headers

Общие Helmet headers устанавливаем до маршрутов, static и ранних ответов. Отключаем X-Powered-By на уровне приложения.
CSP и nonce применяем к HTML, включая ошибки. Не создаём nonce для каждого статического ресурса.

### 22. Production-контейнер и источник версии

Читаем версию package.json непосредственно в env.ts, одинаково при запуске из src и dist. Удаляем требование npm_package_version из схемы.
Общий VERSION используют Context, CACHE_SALT и health.
Контейнер запускается от node-пользователя с прямым CMD node dist/server/server.js. Проверяем права чтения assets и доставку сигнала остановки.
Внешний бюджет остановки контейнера должен позволять приложению завершить согласованные 30 секунд.

### 23. Текст страницы 500

Не добавляем новые элементы интерфейса, ссылки и Request ID. Оформление затем адаптируется под продукт.

### 24. Unhead управляет head

В app.vue читаем lang из стора контекста и реактивно передаём в useHead через htmlAttrs.lang.
Charset и viewport оставляем стандартными настройками Unhead. Убираем их дубли и ручной lang из основного Nunjucks-шаблона.
В независимых шаблонах ошибок и диагностики тоже снимаем запрет масштабирования. Viewport: width=device-width, initial-scale=1.

### 25. HTTP-редиректы из Vue Router

После начальной навигации определяем redirect по redirectedFrom. До prefetch и рендера возвращаем адрес router.resolve(route.fullPath).href.
Код берём из redirectedFrom.meta.responseCode ?? 302. Используем существующий responseCode, без отдельного type или status.
Middleware определяет redirect по 301/302/303/307/308 и отправляет Location. Не считаем весь диапазон 3xx редиректом.
Ответ не кешируем; prefetch, рендер HTML и critical CSS не запускаем.
Текущий внутренний переход на страницу с responseCode 404 сохраняем. Серверный fallback с JavaScript-переходом на клиентскую 404 также сохраняем для дальнейшей навигации.

### 26. Нейтральные настройки шаблона

Проверяем одинаковые URL ресурсов в серверной и клиентской сборках.

По запросу пользователя 10 октября выносим все серверные значения по умолчанию в src/server/env/env-defaults.ts. Схема использует этот источник и сохраняет валидацию явных переопределений.
